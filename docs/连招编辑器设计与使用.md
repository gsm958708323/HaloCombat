# 连招编辑器设计与使用

设计：2026-11-16；实现验收：2026-11-17。架构决策见 [ADR-0048](adr/0048-combo-authoring-intent-and-runtime-explanation.md)。

## 设计目标

编辑器应让作者明确当前配置的操作、玩家输入后的选择依据，以及修改影响哪些内容。节点少不代表配置简单，节点多也不代表一套连招很长。画布首先必须说明自己的编辑范围。

运行匹配是“当前技能 + 输入 + 所需状态 -> 最高优先级目标”，属于显式规则的动态求值。连线表示可能转移，不是自动播放指令；图连通不能证明全部节点属于一套功能。同一技能允许被多个视图引用，图的位置与名称不参与战斗选择。

## 作者操作

| 入口 | 作者完成的任务 | 运行数据 |
| --- | --- | --- |
| 起手绑定 | 空闲时收到输入，启动哪个技能 | 空前置列表的规则 |
| 动作接续 | 当前动作中，在什么条件下接哪个技能 | 明确前置、输入、状态和优先级 |
| 公共取消 | 一组明确动作允许接入闪避等目标 | 一条带多个前置的共享规则 |
| 规则总览 | 检查全表、旧规则用途与全部影响 | 同一份规则，无独立副本 |

独立放炸弹只需一条起手绑定，不强迫创建连招图。连续攻击、派生或循环才适合动作图。公共取消集中维护明确成员，不用“全部动作”替代有限集合。

公开JSON中的可选 purpose 字段使用 entry / transition / cancel，标记作者用途；该字段不限制运行时可用性。旧文件没有该字段时，空前置可以确定为空闲入口；其他规则显示“未标用途”，编辑器不会根据名字、输入或成员数量猜测后静默分类。

## 画布范围与功能视图

从当前技能展开会根据已有接续自动生成后继关系，包括跨输入的分支和循环。默认不把其他动作接入当前技能的全部来源铺开；“其他接入来源”提供显式展开。公共取消不参与动作主图的递归扩散，但影响数量与入口始终可见。

保存功能编排视图时记录名称、根技能、规则ID与布局。视图不复制规则，也不参与运行查表。删除视图保留全部技能和规则。共享一条规则的多个视图会同步受其修改影响，编辑面板列出引用者。视图数量是作者组织数量，不是算法计算出的连招套数。

正式工程预置“连续攻击与派生”和“交替攻击接续”两个项目内容视图；通用编辑器没有硬编码近战、射击或技能身份。其他工程可直接编辑自动展开的关系，按需保存视图，不需要重建已有接续。

    [起手] --主攻击--> [弹药射击]
                            |
                   +--------+----------------+
                   |                         |
            主攻击 + 本次命中          派生A + 本次命中
                   |                         |
                   v                         v
                 [二段]                   [回旋弹]
                   |
            +------+-------------------+
            |                          |
     主攻击 + 本次命中          派生B + 本次命中
            |                          |
            v                          v
          [终结]                     [炸弹]

播放中这些转移都还要求技能接续窗口开启。多个前置表示OR，多个所需Tag表示AND；空前置只匹配空闲，不表示任意动作。

## 编辑与冲突

拖动端口或点击“添加接续”先打开草稿，未应用前不改变运行行为。技能节点引用原定义；双击可进入技能编辑。连线的输入、条件和优先顺序在图下方定位并打开编辑，右侧始终保留当前技能总览。技能窗口使用实际独立或共享时间轴，不保存第二套时序数据。

新增和修改输入、前置、目标、所需状态或优先级，都会针对全表检查重叠：

    已有：A + 攻击 + 命中 -> B，优先级10
    草稿：A + 攻击       -> C

    命中时两条都满足，作者必须决定：
      1. 已有优先：草稿作为后备
      2. 草稿优先：覆盖原候选
      3. 手动设置：明确不同优先级

不同正向Tag可能同时存在，不能把不同Tag当作互斥证明。同优先级、相同输入、前置重叠仍由协议编译拒绝。系统不再根据新增顺序自动提高优先级。优先规则已选中后，同一次查找不会因资源、冷却或目标失败立即尝试低优先级候选。输入未消费且仍在缓冲期时，后续逻辑步继续按实际状态重新求值；命中资格在查表时已消费，后续可能选择另一条规则。

“删除运行规则”会改变行为并同步清理所有视图引用，可撤销；“删除视图”仅改变作者组织。技能改名、替代删除与工程合并会维护技能和规则引用；合并冲突身份时导入视图引用导入的规则，不串到目标工程同名内容。

## 真实预览与反馈

试放区域只发送输入，不通过图路径强制执行技能。正常战斗输入继续经过 InputBuffer、ComboComp 与 SkillCastComp。

图形保持稳定，绿色覆盖表示本次成功执行。运行不会重新选择作者的根技能、挪动节点或触发自动排列。执行路径保留重复技能，循环可显示为 A -> B -> A。窗口等待、状态阻止、无匹配、已选中、施放失败与成功有不同结果；展开候选可以看到当时的窗口、命中资格、缺失状态和优先级。

    当前技能：A；输入：攻击
      -> 等待接续窗
      -> 窗口开启，候选B缺少本次命中
      -> 未接续，输入仍可在缓冲期内等待

    规则选中B，能量不足：
      -> 已选中，但施放失败
      -> 本次成功路径不加入B

    规则请求射击，但缺弹路由到换弹：
      -> 请求技能和实际执行技能分别显示
      -> 本次成功路径记录换弹

诊断由实际匹配调用和施放返回值产生，不在网页重新实现一份求值器。诊断在预览启用，正式角色默认关闭，可按需开启；相同输入、状态和结果不重复逐帧记录。战斗事件最多500条，诊断使用独立的64条历史与独立序号，连招反馈最多取24次成功，输入录制仍默认关闭。纯显示诊断从回放结果投影中移除，不改变原战斗事件序号或已有录制结果。路径开头可能因历史窗口截断而缺失，不把截断处标为真实起手。

## 数据边界与交付

Combat.Core 持有规则定义、动态求值和可选只读决策记录；Combat.Config/Json 校验并转换规则用途、作者视图和预览快照。网页编辑引用、布局与输入，预览宿主和Unity运行同一战斗核。

磁盘保存继续走 SkillProjectFiles 的分片入口；用途存入 runtime/combos.json，作者视图存入 editor.json。完整工程导入导出保留视图；完整运行导出省略 editor，但保留运行规则及用途。单技能F6/F7包继续不携带完整角色输入调度，不能据单技能包还原全部连招规则。

当前匹配器不持有连招方案或阶段上下文。若同一技能B在同样状态和输入下，需要仅因来自A还是X而选择C或D，现有规则无法表达。不能靠在画布复制B解决；此类需求应单独设计真实领域上下文后实现。

## 使用顺序

1. 打开正式内容或自己的工程，进入“连招”。
2. 单技能触发在“起手绑定”配置；多段在“动作接续”选择技能或功能视图。
3. 建立接续并明确输入与条件，处理提示的全表重叠后应用。
4. 配置前置技能时间轴的接续窗口；公共取消在独立入口选择明确成员。
5. 在原预览场景发送真实输入，查看条件、候选与成功执行路径。
6. 保存工程；需要游戏运行时交付时导出完整运行内容。
