# 技能模块化优化建议

日期：2026-11-14。状态：源码审查建议，尚未实施，未接受的提案不构成新的仓库规则。

审查基线：当前 HEAD `1fa8b14`（支持SO配置，新增unity可视化demo）。本轮审查期间工作区发生了版本切换；下面已经按切换后的代码重新核对。此前讨论的 BuffArenaGameplay、通用冷却目录和 ProjectileMotion 策略文件不在当前工作区，不能作为当前已实现能力引用。

产品目标保持不变：独立网页技能编辑器、JSON 唯一内容源、移除 SO 配置；装备、计算公式、地图、冒险四个独立页面不实现。磁盘 AGENTS.md 在切换后不存在，会话中用户提供的工程规则仍适用。

## 模块化的判断标准

复用的是选择目标、检查资源、安排时序、发射、运动、命中、效果与生命周期等战斗能力。新增技能使用已有能力时，应主要新增 JSON 与表现资源绑定；出现真正的新机制时才增加能力实现。

一个网页节点不对应一个 Actor/Comp。按职责选择实现形式：

| 形式 | 内容与状态归属 | 当前例子 |
| --- | --- | --- |
| Definition | 只读共享规则与参数 | ProjectileDefinition、AoeDefinition、DurationSpec |
| Comp | 有实体归属的运行状态与生命周期 | SkillDirectorComp、ProjectileComp、BuffComp |
| Service | 跨实体查询、命中和运行体管理 | ProjectileService、AoeService、HitDetectService |
| Effect | 一次性动作、无共享运行状态 | DamageEffect、SpawnAoeEffect、ApplyDurationEffect |
| Clip handler | 持续区间的开始、推进、结束 | MoveClipHandler、HitboxClipHandler |

Actor.AddComp 按具体类型唯一注册；重复伤害节点应该编译为两次有序 Effect 执行，不能给 Actor 重复添加同一种 DamageComp。

## 当前已有的合理基础

- World.Deliver → EffectPipeline → IEffect 是统一效果边界。
- Timeline 已区分持续 Clip 与离散 Payload，并有 Move、Hitbox、IFrame、CancelTag 的处理入口。
- 投射物/AoE 通过 Definition、Comp、Service 分离规则、每实体状态和跨实体推进。
- DurationSpec、BuffComp、TagComp、属性 Modifier 和召唤物生命周期是可组合基础。
- 目标查询已经有圆形与扇形，不能把“还没接入形状配置”说成“底层完全没有扇形算法”。

这些基础应继续演进，不重新建一套通用图虚拟机、全局管理器或接口森林。

## MOD-01：先建立统一施放入口和成功提交规则

证据：当前 CombatComps.cs:282 的 SkillDirectorComp.Play 只有 skill/timeline 两个身份参数，没有通用技能定义、冷却或能量入口。PlayerCombatDriverComp:372 为 Dodge 使用固定技能/Timeline。

另外，ComboComp.TryResolve 在 :244 解析成功后就消费输入，随后玩家才调用 Play；Play 内 :297 的状态切换返回值也没有参与最终成功判定。这些代码路径需要先核实并修正成功/失败契约，避免在加入冷却和消耗后出现“技能失败但输入/资源已消耗”。

建议新增最小 SkillDefinition 和统一施放协调入口，玩家、AI、调试槽和网页预览都提交技能请求。协调检查状态、目标、资源和冷却，成功开始后才提交消耗与输入消费；SkillDirector 负责播轴与施法生命周期，资源修改归专职属性/资源组件。

冷却只保留一个计时权威，不能在玩家驱动、AI 和网页宿主分别实现。跳跃属于移动能力，实体工厂的类别组装也不是“所有内容必须配置”的理由；只消除真实技能入口里的具体技能分支。

验收：合法/非法目标、能量不足、冷却、Silence/Dead 等拒绝、状态切换拒绝、取消接招和被打断时，返回值与输入/资源/当前技能一致。会话规则要求的自动 Cancel、成功才消费与确认资格必须单独验收，不能假定当前较早版本已实现它们。

## MOD-02：独立表达目标、位置来源和方向

证据：Timeline.cs:342 的 FirePayloads 从行为树黑板获取目标；Effects.cs:117 的 SpawnProjectileEffect 固定从 Source 的位置和朝向发射；SpawnAoeEffect 使用命中点或来源位置。玩家指定点、分裂出生点等没有统一作者语义。

建议为目标选择、位置来源和方向分别提供专用定义与少量解析函数。施法实例保存需要的目标 EntityId、点、方向和快照，按配置明确“施放时锁定”或“触发时重选”。投射物命中派生使用专用事件参数，包含命中点、入射方向和必要父弹状态。

可验证的真实需求：指定方向射击、命中点爆炸、命中点分裂、范围随机选敌闪现。不要给每种需求复制一份 SpawnXxxSkillEffect；也不把 EffectContext 扩成装有全部系统和技能字段的大容器。

## MOD-03：按四个正交维度扩展投射物

证据：RuntimeBodies.cs:198 的 MoveAndHit 目前同时处理追踪、直线推进、寿命和命中；:241 的 SteerHoming 与 :273 的 AcquireNearest 也在该服务。当前没有前面较新快照中的独立 ProjectileMotion 策略。

建议在加入视频已承诺能力时按以下维度拆开：

1. 发射：原点、方向、数量、散射角、发射节奏。
2. 运动：直线、追踪转向，以及实际要实现的加速/回旋/弹跳。
3. 接触行为：穿透、连锁、分裂、重复命中规则。
4. 结果效果：伤害、Buff、范围爆炸、Cue、结束事件。

各维度按实际需要增加明确的算法或策略，运动只计算运动，命中/寿命由服务协调；新增运动策略时再引入有真实多实现的边界接口。连锁次数、分裂代数、已命中集合、伤害倍率等可变信息归单颗 ProjectileComp，不写回共享定义。

直线发射、随机散射和命中分裂都应复用同一底层生成流程，不创建 FireballManager、SplitShotManager 这类逐技能工具。射程、寿命、碰撞半径和爆炸半径分别表达，不能只因直线示例可用 range/speed 就假定所有弹道等价。

## MOD-04：让技能成为通用效果与生命周期的组合

证据：Timeline.cs:49 起直接放 G1/G2/Dodge/Homing 等默认时间轴；Factory.cs:74 固定装备默认技能，:80 起按蓝图构造特定 AI 与技能；DemoTables.ResetG1MeleeDefaults 修改 TimelineSO.G1Melee 的共享默认效果。

这些是当前示例内容的来源，不应继续成为网页新增技能的代码入口。迁移 JSON 后，生产内容由定义生成，示例表若保留则放在独立样例/测试路径，不能成为加载失败回退。只读 TimelineDefinition 不再承担具体技能的静态构造和全局默认数据重置。

保留现有 Effect、Buff、Clip 的边界：一次伤害/生成/传送用 Effect，持续移动/无敌/判定用 Clip，持续属性与周期效果用 Buff，独立寿命对象用 Actor。无需为每个节点创建 Comp，也不把持续行为塞进一次性回调。

现有召唤的归属/寿命与未来爆炸陷阱可复用生成、拥有者、死亡/到期效果等能力；真正独有的目标入伤规则可以保留具名产品组件。不要为尚不存在的所有物件预造“任意规则 DSL”。

## MOD-05：先保证组合过程可重入、可跨世界隔离

证据：RuntimeBodies.cs:133 的 AoePulse 共用 static Actor[32]；该函数遍历目标时直接投递效果，效果若同步生成另一个立即脉冲 AoE，会再次使用同一缓冲并覆盖外层目标列表。多个预览世界也共享这份数组。

同文件 :161、:315 等查询缓冲为 32 项；QueryRandom.cs:52 到容量就停止，没有显式表示结果被截断。新技能的大范围和分裂/连锁组合会更容易碰到容量与重入边界。

建议使用调用者拥有、容量明确的查询结果；需要完整范围结算时保证收齐或明确报告截断。嵌套投递不能复用外层仍在遍历的存储；可用调用级结果或有作用域的复用缓冲，不能只把 static 改为单个服务字段就宣称修好了同世界重入。

另一处生命周期边界在 Buffs.cs:55：Buff 实例长期保存 Actor Source。建议保存完整 EntityId，触发时从所属世界解析，已失效来源按无来源处理；尤其要覆盖对象池复用，避免旧 Buff 指向同一个 C# Actor 对象所承载的新实体。

验收：同步嵌套 AoE、超过32个目标、两份独立世界、来源销毁/复用、同定义多弹体/多次施法不串状态。这些保障会直接影响“模块可组合”，优先于泛化大量控件和接口。

## MOD-06：JSON 只负责编译内容，不成为运行时万能节点系统

节点 kind、字段、单位、默认值、端口和运行能力要有明确协议。图通过 Combat.Config 校验转换成 Timeline/Projectile/AoE/Buff/Skill 等定义；运行时不逐帧查图，不通过反射执行任意类或脚本。

新增基础能力时补齐前端控件、协议校验、领域转换、执行和测试；已有能力组成新技能时不再补按 skillId/name 分派的代码。按 damage/projectile/split 等能力类型分派是合理实现，不需要为了消除 switch 再建设插件框架。

图形位置、折叠状态和节点选择不进入业务判断。Definition 与每次施法/运行实体状态分离，Effect 不保存自己的目标列表、触发计时或父弹运行态。

## MOD-07：每次加载建立完整快照，删除旧 SO 路径

证据：BakedContent.cs:16 的 Install 通过 World.ReplaceCatalogs/ReplaceCues 在构造后替换目录；SkillDirector 自己持有 TimelineLibrary。这种装配方式在发布新配置时需要明确整体一致性，不能只替换部分目录。

JSON 迁移建议读文件、校验依赖、转换所有定义后，一次安装新世界快照。预览重置/游戏重载创建新会话；旧弹体、Buff 和时间轴不混用新定义。删除完成迁移的 SO/Bake/cache 与 fallback，而不是给新旧内容源包一个永久兼容入口。

当前 RuntimeBodies.cs 的 Catalog.Register 对重复 ID 直接覆盖；正式 JSON 路径需要提前拒绝重复身份、未知类型、缺失引用和递归，并带技能/节点/字段路径。网页能画出连线不等于游戏已经接受其语义。

## MOD-08：按职责组织文件，不追求组件数量

当前较早快照的 Core 最大文件为 RuntimeBodies.cs 433 行，不能沿用切换前“多个 Core 文件超500行”的结论。随着新增能力，优先按定义/组件/服务与 Combo/SkillDirector/输入驱动等真实边界拆分。

旧Config作者类型DefinitionAssets/EffectAssets及同名partial壳现已按ADR-0015删除；JSON DTO、显式转换和Core领域定义承接原值。此处的原始审查证据反映早期基线，不能视作这些SO仍在正常运行。

保持现有合法接口和模块依赖，避免新增接口森林、全局 Manager、反射组件组装及无界 Context。命名具体、用途单一的类型比一个带几十个布尔开关的 UniversalSkillComp 更容易维护。

## 用组合验证复用价值

以下是目标表达，不表示已经实现：

```text
爆裂弹 = 指定方向 + 瞬发 + 直线弹 + 命中范围伤害 + 爆炸 Cue
连锁弹 = 同一发射/运动 + 连锁接触行为 + 同一伤害模块
分裂弹 = 同一发射/运动 + 命中点派生发射 + 子弹定义 + 同一伤害模块
闪现斩 = 范围选敌 + 合法落点传送 + 扇形判定 + 同一伤害模块
```

一个能力用多种已承诺技能验证，不要求所有产品独有规则都强行通用化。技能的名字留在 JSON/显示内容；真正的新算法使用连锁、分裂、扇形判定这样的能力名称实现。

## 建议实施顺序与验证边界

优先 MOD-01/02/05，建立可靠施法、数据传递和组合安全；MOD-06/07 接通 JSON 唯一内容路径；MOD-03/04 随视频已承诺技能逐项实施；MOD-08 随职责整理完成。

已有机制的新组合应主要改 JSON；新增机制要有一份明确的运行实现，并由所有调用入口复用。重点验证失败不消费、取消/打断清理、输入与时钟、不同目标/位置、嵌套触发、父实体失效、跨世界和对象池复用。

当前仓库 README 列出了 regress、lesson、training-camp，PlayMode 有教学场景加载用例；这些是已有测试入口，不是本轮通过记录。实施后 Core 运行 build/regress，Unity 变更运行编译与相关 EditMode/PlayMode；浏览器和 C# 也需做同定义、初始条件、输入与随机规则的结果对照。

本轮只审查并整理建议，没有修改运行时代码、资产或配置，没有执行构建或测试。
