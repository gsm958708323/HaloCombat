# 玩家技能实现详解（Buff Arena · Combat.Core）

> 一句话总纲：**玩家的"技能"不是一个类，而是「四层数据 + 一个播放器 + 一条固定帧序」。**
> 技能 = 输入令牌 → 技能定义(SK) → 时间轴(TL) → ｛时间片 Clips ｜ 时间点 Payloads｝ → 效果 IEffect → 服务（弹道 / AoE） → 唯一结算入口 `World.Deliver`。

本文按"数据长什么样 → 一帧怎么走 → 每段为什么这么切"来讲。所有结论都标了出处文件与行号，可以直接跳去看代码。

四层各自的"可变性"是这套设计的核心：

| 层 | 生命周期 | 能不能写 |
|---|---|---|
| `BuffArenaData`（技能/时间轴/弹道/AoE/Cue） | 一局一份，跨实体共享 | **只读**。写回去重开局会串场 |
| `TimelineSO` / `TimelineClip` / `TimelinePayload`（烘焙结果） | 同上 | **只读**。运行时状态全在播放器里 |
| `SkillDirectorComp` / `TimelinePlayer` / `LocomotionComp` | 每角色一份 | 可写。严禁跨实体共享 |
| `Actor` / 实体（子弹、AoE） | 池化复用 | 可写，`Release` 时 `ResetForPool` 重置 |

## 1. 数据模型：四种 id 和一条资产链

### 1.1 四种 id，各管一段

| id 类型 | 定义处 | 例子 | 语义 |
|---|---|---|---|
| `InputToken` | `Primitives.cs:162` | `"Fire1"`、`"Roll"` | 字符串值语义，**按键侧与资产侧必须逐字相等** |
| `SkillNodeId` | `Primitives.cs:106` | `2001`、`2011` | 技能身份，不透明 id |
| `TimelineId` | `Primitives.cs:140` | `3001`、`3010` | 时间轴身份 |
| `SpecId` | `ProjectileDefAsset` / `AoeDefAsset` | `4001`、`4102` | 弹道 / AoE 身份 |
| `CueId` | `CueLibrary` | `4201`、`4204` | 表现事件身份 |

`InputToken` 那条契约最脆——对不上时**不报错**，`FindByInput` 返回 null，这次输入被静默丢弃（`BuffArenaGameplay.cs:289`）。PlayMode 测试 `EveryKeyCastsItsSkill`（`BuffArenaSkillSmokeTests.cs:166`）就是为这条契约兜底的。

### 1.2 一条完整引用链（以最典型的 SK_2001 为例）

```
 按键 "1" / 鼠标左键
      │  BuffArenaInputSource.Sample          → Fire1Held = true
      ▼
 BuffArenaInputFrame ──ApplyInput──► buffer.Push(InputToken("Fire1"))
      │                                    ▲  BuffArenaIds.Fire1（代码拥有的键位表）
      ▼

      │                                          Id=2001 Timeline=3001 AmmoCost=1
      │                                          FallbackSkill=2009
      ▼

      │  ├─ 守卫：Dead/Stunned/Downed/Silence → 拒绝
      │  ├─ 守卫：TL 缺失 → throw（配置错误不静默）
      │  ├─ loco.RequestSnapYaw()（起手先吸附朝向）

      ▼

      │
      ├─ PlayBuffArenaCueEffect(4201,"Muzzle") ──► Events.Publish(EvCue) ──► CueDirector ──► VFX池
      └─ SpawnProjectileEffect(4001) ──► Intents.Post(SpawnProjectileIntent)

                                        Actor("projectile") + ProjectileComp(PD_4001)

**关键点：`SpawnProjectileEffect` 不生成子弹，它只投一个意图。** 效果实例可能在多条内容之间共享，所以它必须无状态——携带的 `SnapshotAtk` 必须在投递当帧定死（`Effects.cs:123-144`）。

### 1.3 资产是怎么烘焙的（四步，任一步失败即拒绝开局）

```
   BuffArenaDatabaseAsset.Bake()                        BuffArenaDatabaseAsset.cs:60
     │
     ├─① HasCompleteContent()      数组非空且无 null 洞 + Motor 已赋值
     │      失败 → LastContentError = IncompleteReason，返回 null
     │
     ├─② BakeCore()                逐个 Bake() 并 Register
     │      · Timelines.Register()   重复 Id / Id=0  → throw（Timeline.cs:172）
     │      · Projectiles.Register() 同上（RuntimeBodies.cs）
     │      · Skills.Add()
     │      · BakeActors()
     │      └─ HasCastlessPayload() payload 里残留 null 效果槽 → 返回 null
     │            （注释原话：带着空洞开服等于放出"有施法动作、什么也不生成"的技能）
     │
     ├─③ ValidateReferences()      交叉引用 + 数值校验
     │      · 三个蓝图 buff_player / buff_enemy / buff_barrel 必须存在
     │      · 每个技能指向的时间轴必须存在
     │      · FallbackSkill 必须存在
     │      · PlayerMaxHp / PlayerAmmoCapacity / MaxEnemies / SpawnPeriod … 必须为正
     │
     └─④ 返回 BuffArenaData          调用方 BuffArenaBootstrap 拿不到就直接让会话启动失败
```

设计意图（资产文件头注释写得很直白）：**"默认值会把'内容没配好'伪装成'游戏本来就这样'"**，所以这套内容路径**没有任何代码回退**。

## 2. 一帧的三条时间线

### 2.1 双时钟：wall 永不冻结，logic 会被顿帧停摆

```
   真实时间 ──────────────────────────────────────────────────────────►
                 dt=16.7ms        dt=16.7ms        dt=16.7ms
   wall 钟   ├────────────┼────────────┼────────────┤   一直走
              帧号+1        帧号+1        帧号+1
                                                  ▲ 顿帧（Hitstop）发生在这里
   logic 钟  ├────────────┼────────────┼    ┊    ┊    ┊    ┊├────────────┤
              AdvanceLogic  AdvanceLogic  PauseLogic × N 帧后恢复
                                          （Delta 置 0，Time 不动）

   后果：顿帧只冻结模拟，表现层（VFX 池、UI、镜头）照常推进 —— CombatTime 文档注释
```

`CombatTime` 里有两组字段（`Infrastructure.cs:12-65`），踩坑点是 **`Frame` 由 `AdvanceWall` 自增（墙钟帧号），模拟步数必须看 `LogicFrame`**，两者不可混用。

### 2.2 逻辑帧的 9 段固定顺序（`World.Tick`，`World.cs:224-297`）

```
   ┌───────────────────────────────────────────────────────────────────────────────┐
   │ CombatWorld.Tick(dt)                                                          │
   ├───────────────────────────────────────────────────────────────────────────────┤
   │ 0. AdvanceWall(dt)                         ── 墙钟永远推进                     │
   │    if (顿帧中) { PauseLogic(); 帧数--; FlushDespawn(); return; }  ← 直接返回    │
   │ 1. AdvanceLogic(dt) + 对所有活跃 Actor 跑 TickAll(dt)                          │
   │      ★ 玩家的输入读取 / 技能播放 / 时间轴推进都在这一段                          │
   │        组件按 AddComp 顺序 Tick（ActorModel.cs:97）                            │
   ├───────────────────────────────────────────────────────────────────────────────┤
   │ 2. LocomotionComp.IntegrateBeforeHitDetection(dt)     ← 常规移动 + 技能位移     │
   │      "让判定用的位置与本帧已积分的位置一致"                                      │
   ├───────────────────────────────────────────────────────────────────────────────┤
   │ 3. ProjectileService.Tick(dt)   先 DrainSpawns（消费阶段1投的发射意图）再 Move/Hit│
   │    HitDetectService.Tick()      扫所有打开的 HitboxComp 做圆查询                │
   │      两者都只 Post(ApplyEffectsIntent)，不结算                                  │
   ├───────────────────────────────────────────────────────────────────────────────┤
   │ 4. Intents.Drain<ApplyEffectsIntent>  ──► World.Deliver(...)  ★ 唯一结算路径    │
   ├───────────────────────────────────────────────────────────────────────────────┤
   │ 5. SkillDirectorComp.FlushTimeline()   ── 时间轴收尾（到期且 clip 全关才通知结束）│
   ├───────────────────────────────────────────────────────────────────────────────┤
   │ 6. AoeService.Tick(dt)                 位移 / 吸附 / 占用差分 OnEnter / 脉冲 / 寿命│
   ├───────────────────────────────────────────────────────────────────────────────┤
   │ 7. BuffComp.Tick(dt)                   周期结算                                │
   ├───────────────────────────────────────────────────────────────────────────────┤
   │ 8. LocomotionComp.IntegrateAfterHitDetection(dt)  ← 击退 + 重力               │
   ├───────────────────────────────────────────────────────────────────────────────┤
   │ 9. EntityRegistry.FlushDespawn()        延迟销毁真正生效                        │
   └───────────────────────────────────────────────────────────────────────────────┘
```

为什么第 2 段和第 8 段必须分开、第 6 段为什么在效果之后，`框架与子系统优化方案.md` §4.3 有完整论证。这里只记结论：**阶段顺序就是结算语义，不是实现细节**，所以优化方案里明确写了"不把 5 个阶段合成一次遍历"。

### 2.3 一次"按 LMB"横跨的帧（放大看）

```
 帧 N                    ┌── 阶段1 ──────────────────────────────────────────┐
                         │ Actor.TickAll 按组件顺序:                          │
                         │   HealthComp → StateMachineComp → SkillDirector   │
                         │      （此刻还没播技能，IsPlaying=false，直接 return）│
                         │   → BuffArenaPlayerComp                          │
                         │        TryPeek("Fire1") → Consume → FindByInput    │
                         │        TryConsume(1 ammo) OK                       │
                         │        director.Play(2001, 3001)  ← 时间轴 _time=0 │
                         │        fsm.TryEnter(Attack) → 挂 Casting 标签      │
                         └───────────────────────────────────────────────────┘
                         ★ 本帧时间轴不会被推进：导演排在玩家驱动之前
 帧 N+1                 ┌── 阶段1 ──────────────────────────────────────────┐
                         │ SkillDirector.Tick → TimelinePlayer.Tick(dt)       │
                         │   prev=0, next=dt                                  │
                         │   OpenIntersecting / TickLive / MarkDueClose       │
                         │   FirePayloads(prev=0) → t=0.1 若 dt≥0.1 则本帧投递  │
                         └───────────────────────────────────────────────────┘
                            └─ 阶段2 若同时开了 Move clip，位移在本帧生效
                            └─ 阶段3 若本帧投了 SpawnProjectileIntent，子弹本帧就飞一帧
```

组件 Tick 顺序由 `AddComp` 决定（`ActorModel.cs:48,97`），玩家的装配顺序见 `BuffArenaActorFactory.Combatant`（`BuffArenaGameplay.cs:662-694`）：`SkillDirectorComp` 在 `AmmoComp` / `InputBufferComp` / `ProjectileTrackerComp` / `BuffArenaPlayerComp` **之前**。

```
   ┌─────────────── InputSystem_Actions.inputactions（Gameplay 图）───────────────┐
   │ Fire1 = 1 / 鼠标左键      Fire2 = 2 / 右键      Fire3 = 3 / 中键              │
   │ Fire4 = 4 / 侧键后退      Fire5 = 5 / 侧键前进                                 │

                                   │   · AimYaw 来自相机穿鼠标射线与地面交点

                        ▼
        ┌──────────────────────────────────────────────────────────┐
        │  单槽位状态机                                             │
        │                                                          │

        │                        │                                 │

**为什么是"单槽位 + 后推者胜"**：源工程的 `PlayerController` 就是这个顺序，移植时保留。副作用是**同时按住两个键只有优先级高的那个生效**，而另一个的按下事件直接丢失（不是排队）。

`ApplyInput` 还有三条整帧丢弃的入口（`BuffArenaSession.cs:94-97`）：已 Dispose、玩家已死、玩家 Actor 不存在。

### 4.1 两条回退链的对比

```
                     ┌─ 正常 ─────────────────────────────────────────────┐
   Fire1(SK_2001) ───┤  AmmoCost=1，扣 1 发 ──► TL_3001 ──► 弹道 PD_4001    │
                     └────────────────────────────────────────────────────┘
                     ┌─ 回退（弹药付不出）──────────────────────────────────┐
                     │  FallbackSkillId = 2009 (Reload)                    │
                     │  ──► TL_3009  Duration=1.15  AnimatorState="Reload" │
                     │       payload t=1.1: RefillAmmo(60)  ← 一发自补满     │
                     └────────────────────────────────────────────────────┘
                     ┌─ 改写（传送弹已在飞）────────────────────────────────┐
   Fire4(SK_2006) ───┤  RequiresTrackedProjectile=1, WarpSkillId=2011        │
                     │  弹在飞 ──► TryTeleport()：直接传送到弹的位置          │
                     │  弹不在  ──► 落回普通施放 ──► TL_3006 ──► 弹道 PD_4004 │

### 5.2 时间轴推进：半开区间 `(prev, now]`

`TimelinePlayer.Tick` 的注释把顺序写死了（`Timeline.cs:346-367`）。这是整个技能系统里最需要精确理解的一段。

```
  时间轴（TL_3001：Duration=0.5，payload 在 t=0.1）
    t: 0 ────────────── 0.1 ────────────────────────────────────── 0.5
                        ●
                      payload

  帧推进（dt 不均匀 → 用半开区间保证"每点恰好投递一次"）
                                                              
  帧1: prev=0.000, next=0.033   (0.000, 0.033]  → 未到 0.1
  帧2: prev=0.033, next=0.066   (0.033, 0.066]  → 未到
  帧3: prev=0.066, next=0.099   (0.066, 0.099]  → 未到
  帧4: prev=0.099, next=0.132   (0.099, 0.132]  → ★ 命中 0.1，投递一次
  帧5: prev=0.132, next=0.165   → 已 _payloadFired，跳过
  ...
  帧N: next 触到 0.5（clamp 到 Duration）→ _finishPending = true

  ★ 首帧兜底：prev <= 0 时，所有 t <= _time 的 payload 都会被投递
    （半开区间 (0, dt] 会漏掉 t == 0 的条目）
    副作用：若某帧 dt ≥ 0.1，t=0 和 t=0.1 会在同一帧一起投递
```

同一帧内的固定处理顺序：

```
   ┌───────────────────── TimelinePlayer.Tick(dt, self) ─────────────────────┐
   │ prev = _time ;  next = clamp(_time + dt, ≤ Duration, ≥ prev)             │
   │                                                                         │
   │ ① OpenIntersecting(prev, next)   本帧首次与 (prev,next] 相交的 clip 立即 Open│
   │       条件：End > prev && Start < next（_clipOpened[i] 保证只开一次）      │
   │       ★ 先 Open 再算本帧 Tick 区间 → 起手帧不丢                            │
   │ ② TickLive(prev, next)           只对交集区间 Tick，dt = ActiveDelta      │
   │ ③ MarkDueClose(next)             now >= End 的只"标记待关"，不当场删        │
   │ ④ _time = next                                                            │
   │ ⑤ FirePayloads(self, prev)       投递到期 payload                         │
   │ ⑥ _time >= Duration → _finishPending = true                              │
   └──────────────────────────────────────────────────────────────────────────┘
                                     │
                                     ▼
   ┌──────────── FlushPendingCloses()（由 World 阶段 5 调用）─────────────────┐
   │ 倒序扫描 _live：ClosePending 的 → Handler.Close(rt, interrupted:false)    │
   │                 → 从 _live 移除                                          │
   │                                                                          │
   │ 返回 true 的条件：_finishPending && _live.Count == 0                      │
   │   → 只有此时调用方（SkillDirectorComp.FlushTimeline）才复位当前技能         │
   │     并 fsm.NotifyActivityFinished(Attack)                                │
   └──────────────────────────────────────────────────────────────────────────┘
```

**为什么要"先标记、后关闭"**：`OpenIntersecting` 可能在同一帧新开 clip，当场从 `_live` 移除会破坏正在遍历的列表。所以 Close 一律推迟到 `FlushPendingCloses`。

### 5.3 ClipRuntime：切片视图

`ClipRuntime`（`Timeline.cs:189-200`）把"本帧推进区间"和"与 clip 区间的交集"分开：

```
         clip 区间 [Start ───────────────────────── End)
                       │                            │
   本帧步进区间         │   (StepStart ──── StepEnd]  │
                       │        │                    │
   交集（ActiveStart ───┼────────┴──── ActiveEnd)    │
                       │                            │
                       ▼                            ▼
   ActiveDelta = max(0, ActiveEnd - ActiveStart)  ← Handler 只能拿它当 dt

   为什么必须这样切：
     · 首个相交帧只结算"实际重叠的那部分"，不会把 clip 开始前的时长也算进去
     · 跨帧补偿（掉帧后 dt 变大）时不多算
     · ActiveDelta == 0 时不调用 Tick，避免给 Handler 传空 dt
```

### 5.4 时间轴的许可位三兄弟

| 属性 | 表达式（`CombatComps.cs:302-306`） | 没在播放时 | 用途 |
|---|---|---|---|

### 6.1 四种 `ClipKind` 的语义

|---|---|---|---|---|---|
| `CancelTag` | 1 | `CancelTagClipHandler` | 挂一层 `Cancel` 标签（来源 `Clip.Cancel`） | 无 | 按**同一来源**移除一层 |
| `Move` | 2 | `MoveClipHandler` | 缓存整段位移（按 `FacingForSkillMove()` 旋转到世界系）与时长；`SetClipSteer(Steer)` | 按 `dt/总时长` 发 `RequestSkillDelta`，`k` 夹到 1 | `ClearClipSteer()`（否则转向权重会残留到下一段动作） |

两个"挂标签"型 Handler 都用 `TagSource.Effect("Clip.XXX")` 作为来源，配合 `TagComp` 的计数语义（`TagsInput.cs:15-33`）：

```
   来源A 加 1 ─┐
   来源B 加 1 ─┼─► _stacks[Invincible] = 2    Has() = true
   来源A 减 1 ─┘                              _stacks = 1，Has() = true  ← 不会被误清
   来源B 减 1                                 移除键，Has() = false
```

所以 `Clip.IFrame` 关闭时**不会**清掉 `HealthComp.BeginIFrame` 给的无敌——两条来源各自记账。这是防止"技能无敌帧结束顺带把受击无敌也清了"的关键。

`Move` 处理器里的本地→世界旋转（`Timeline.cs:269-275`）：

```
   资产里写的是本地系：+Z 是朝向正前、+X 是角色右手（见 TransformComp 的 yaw 约定）
      世界位移 = RotateLocal(MoveX, MoveY, MoveZ, yaw)
                 x' = x·cos + z·sin
                 z' = -x·sin + z·cos
   yaw 取自 FacingForSkillMove() = 有 SnapYaw 用 SnapYaw，否则用当前 yaw
      → 技能起手先吸朝向，之后的整段位移都基于这个朝向
   按 dt/总时长 均摊 → 帧率变化不改变总位移
```

### 7.2 蜂腰：所有内容最终只有一个结算入口

```

   子弹 OnHit     ─┼──► World.Deliver(effects, source, target, snapshotAtk, point?, dir?)
   AoE 脉冲/进入  ─┤              │
   木桶爆炸       ─┤              ▼
   反伤 / Buff周期 ─┘      EffectPipeline.Run(ref ctx, effects)   ← 唯一入口

`Deliver` 有两个入口形态：

```
   ① 直接调用：World.Deliver(...)                      —— 时间轴 / AoE / 木桶 / 演示
   ② 意图队列：Intents.Post(ApplyEffectsIntent)        —— 子弹命中 / 判定盒命中
                → 阶段4 Drain → TryGetActor(src/dst) → Deliver
```

为什么命中要走队列？因为**阶段 3 只负责"发现命中"，阶段 4 才结算**——这样一帧内的所有命中在同一个位置统一结算，不会出现"边遍历实体边改血量"的重入。

### 7.3 命中检测：判定盒 + 去重

```
   HitDetectService.Tick（QueryRandom.cs:141-167）
     for 每个活跃 Actor:

        center = CombatGeom.HitboxCenter(tf, box)       ← 本地偏移转到世界
        n = Query.OverlapCircle(center, box.Radius, attacker, 0, buffer)
        snapshotAtk = attacker.AttributeSet.GetFinal(Atk)   ← 取"当帧最终 Atk"
        for 每个 victim:

`HitboxComp` 的去重键把 `EntityId` 压成 `long`（`Index << 32 | Generation`，`CombatComps.cs:103`），`Open`/`Close` 都会清空记录。子弹同理但多一层 `SameTargetDelay` 冷却（到期后同一目标可再命中）。

**无敌目标不消耗命中次数**——`MoveAndHit` 里对 `HealthComp.IsInvulnerable` 是 `continue` 而不是记一次命中（`RuntimeBodies.cs:439-441`），对齐源工程 `CanHit` 的 `immuneTime` 提前返回。

## 8. 位移为什么要在命中前后各积分一次

### 8.1 三只意图池 + 一个瞬移槽

`LocomotionComp` 不自己决定什么时候动，它只是**收集意图**，由世界在两个时刻统一积分（`Motor.cs:35-50`）：

```
   ┌── 写入方 ──────────────────────────────┐   ┌── 池 ──────────┐   ┌── 生效时刻 ──┐
   │ RequestMoveIntent(x,z)   操控/行为树    │──►│ _moveIntent    │──►│ 阶段2（常规） │
   │ RequestAimYaw(yaw)       相机瞄向       │──►│ _aimYaw        │──►│ 阶段2（朝向） │
   │ RequestSkillDelta(x,y,z) Timeline Move │──►│ _skillDelta += │──►│ 阶段2（技能） │
   │ RequestHitDelta(x,y,z)   击退/拉拽     │──►│ _hitDelta   += │──►│ 阶段8（击退） │
   │ RequestTeleport(pos)     瞬移           │──►│ _teleport      │──►│ 阶段2（最先） │
   │ RequestSnapYaw()         起手吸朝向     │──►│ _pendingYaw    │──►│ 阶段2（最先） │
   └────────────────────────────────────────┘   └────────────────┘   └──────────────┘
```

三个 delta 池都是 `+=`（叠加），只有 `_teleport` 是覆盖，`_moveIntent` 是覆盖。

### 8.2 为什么必须是两个时刻

```
      阶段2 积分前 ──► 位置 P2 ──► 阶段3 用它做判定盒圆心与子弹出生点
                                     │
                                     │  ← 如果击退也在阶段2生效：
                                     │     判定的位置 = 已被击退推开的位置
                                     │     视觉上的碰撞盒与查询用的位置不一致
                                     ▼
      阶段8 积分后 ──► 位置 P8 ──► 击退/重力在这里才改写位置
                                     │
                                     ▼
      下一帧的阶段2 用 P8 作为起点 ──► 视觉与判定始终一致
```

世界里的注释就是结论（`World.cs:252-253`）：**"Apply regular and skill movement before hit detection so the displayed hitbox and the position used for the actual query describe the same frame."**

```
  ┌─────────────────────────────────────────────────────────────────────┐
  │ 帧内位置的两条时间线                                                  │
  │                                                                     │
  │  P_start ──[阶段2: 常规+技能位移+瞬移+吸朝向]──► P_hit ──[判定]──►    │
  │                                                  │                  │
  │                                        [阶段8: 击退+重力]           │
  │                                                  ▼                  │
  │                                              P_end = 下帧 P_start    │
  └─────────────────────────────────────────────────────────────────────┘
```

### 8.3 技能位移与常规移动的优先级

`MotorScale` 决定常规移动的缩放（`Motor.cs:247-254`），而**技能位移永远 100% 叠加**（只要 `loco.UseSkill` 为真，由活动策略给出）。`Attack` 活动的策略是 `MotorScale=0, UseSkill=true, ApplyGravity=true, Facing=SteerIfGrounded`（`Activity.cs:95-99`）——也就是**攻击时常规移动被压成 0，技能位移照走**。

朝向策略 `FacingMode` 三态：

```
   FollowStickIfGrounded   Root：落地时朝摇杆方向
   Lock                    Hit / Dead / Knockdown：锁死，不许转
   SteerIfGrounded         Attack：只有 clip 的 Steer > 0 且落地且推摇杆才转
   ★ 但鼠标瞄准（_hasAimYaw）只要 Mode != Lock 就优先，按 AimTurnRate=3600°/s 逼近
     —— 注释解释：源工程在技能时间轴期间仍然每 FixedUpdate 调 OrderRotateTo
```

## 9. 打断与状态机：技能不是孤岛

### 9.1 五个活动与转换表

```
                        ┌───────────────────────────────┐
                        │            Root               │
                        │  1.0 倍移动 / 跟摇杆转向 / 重力 │
                        └───┬───────────┬───────────┬───┘
        TryEnter(Attack)    │           │ HitStun   │ KnockdownEffect
        （任何 Play 成功）   │           │           │
                            ▼           ▼           ▼
              ┌──────────────────┐ ┌──────────┐ ┌───────────────┐
              │      Attack      │ │   Hit    │ │   Knockdown   │
              │ 0 倍移动/可用技能 │ │ 锁朝向   │ │ 0倍移动/锁朝向 │
              │ 挂 Casting 标签   │ │ 挂 Stunned│ │ 挂 Downed 标签 │
              │ 靠时间轴结束退出  │ │ 计时退出  │ │ 计时退出       │
              └────────┬─────────┘ └────┬─────┘ └───────┬───────┘
                       │                │               │
                       └────────────────┴───────────────┘
                                        │ Hp <= 0（DamageEffect 里 fsm.TryEnter(Dead)）
                                        ▼
                              ┌───────────────────┐
                              │       Dead        │
                              │ 拒绝一切转换       │
                              └───────────────────┘
```

转换守卫（`StateMachineComp.TryEnter`，`Activity.cs:288-327`）：

```
   当前是 Dead                → 一律拒绝
   Hit → Hit / Knockdown → Knockdown  → "刷新"（Refresh：重置计时，**不重复挂标签**）
   next == 当前                → 直接 true（空转换）
   当前是 Hit                 → 只允许 Dead / Root / Knockdown
   当前是 Knockdown           → 只允许 Dead / Root
   否则                        → target.CanEnter(from) 判定
```

### 9.2 谁在打断技能

```
   ┌─ HitStunEffect ─────────────────────────────────────────────────────┐
   │  SuperArmor / Dead / Downed → 直接吞掉（不打断）                       │
   │  否则 fsm.TryEnter(Hit) → HitActivity.ApplyHit:                      │
   │      ctx.Input?.Clear()              清掉缓冲输入                     │
   │      ctx.Director?.Stop(reason:Hit)   停时间轴                       │
   │      ctx.Loco?.ClearClipSteer()       清 clip 转向                   │
   │      ctx.Loco?.ClearPendingSkill()    清未结算的技能位移                │
   │      hp.BeginIFrame(args.IFrameDuration)  可选受击无敌                │
   └─────────────────────────────────────────────────────────────────────┘
   ┌─ KnockdownEffect ──► KnockdownActivity.Apply：同上四步，Stop(reason:Knockdown) │
   ┌─ 死亡 ──► DeadActivity.Enter：Clear 输入 + Stop(reason:Dead)               │
   │           + NotifyDeath + Buffs.ClearAllWithExpire                        │
   │           + World.CleanupByOwner(Self.Id)  ← 清掉自己生成的子弹/AoE/召唤物  │
   │           + Events.Publish(EvEntityDead)                                  │
   ┌─ 被打断时 TimelinePlayer.StopInternal(interrupted:true) ────────────────┐
   │  所有存活 clip 的 Handler.Close(rt, interrupted: true)                   │
   │      → CancelTag 标签被移除、IFrame 标签被移除、ClipSteer 被清           │
   │  这就是"打断必须走 Stop 而不是直接丢弃播放器"的原因：标签泄漏会让角色       │
   │  永久无敌 / 永久带 Cancel。                                              │
   └─────────────────────────────────────────────────────────────────────────┘
```

技能正常结束与被打断的区别就在这里（`DirectorStopReason`，`CombatComps.cs:7-16`）：

```
   Finished  ← FlushTimeline 走完全程（clip 全关 + 到期）
   Replaced  ← Play 时覆盖上一段
   Hit / Dead / Knockdown / Detach / Manual  ← 被外力打断
```

`DirectorStopReason` 只给调用方区分上下文（表现/日志），**不参与结算**。

### 9.3 技能结束的"两段式"通知

```
   时间轴到期            clip 全部关闭             技能才算结束
   _time >= Duration  &&  _live.Count == 0   ──►  FlushPendingCloses() == true
          │                      │                        │
      _finishPending=true    逐个 Close              复位 _currentSkill
                                                        fsm.NotifyActivityFinished(Attack)
                                                         → TryEnter(Root)
```

世界在**阶段 5** 才调用 `FlushTimeline`（在效果排空之后），所以"这一帧的最后一发伤害已经结算完了"才切回 Root，不会提前打断收尾动作。

## 10. 表现层怎么跟上

```
   逻辑（阶段1..9）                                表现（LateTick / PumpPresent）
   ─────────────────                              ────────────────────────────
   Actor 状态
     ├─ TagComp         (Grounded/InAir/Downed/Dead/Invincible/Cancel/Casting)
     ├─ StateMachineComp(Current)          ──►  AnimationPresent.SyncLogic
     ├─ SkillDirectorComp(IsPlaying,                 └─ AnimFlags.Capture(a, hitstop)
     │   CurrentSkill, CurrentTime,                       │
     │   CurrentDuration, AnimationMode)                  ▼
     └─ LocomotionComp(MoveIntent)              AnimationPresent.LateTick
                                                   SetBool("Grounded"/"InAir"/"Attack"/
                                                     "Hit"/"Downed"/"Dead"/"IFrame"/"Hitstop")
                                                   SetFloat("Speed")
                                                   SetInteger("SkillId")
                                                   SetFloat("SkillTime"/"SkillDuration")
   Events.Publish(EvCue)                 ──►  CueDirector.OnCue → UnityVfxPool / 音效
   Events.Publish(EvEntitySpawn)         ──►  生成 view（按 ViewBlueprintId 查表）

两条契约：**表现只读逻辑快照**（`AnimationPresent.SyncLogic` 在逻辑之后抓一次，`LateTick` 只应用），**表现不驱动逻辑**（除了把 `EvCue` 转成特效播放）。

`HudSnapshot`（`HudSnapshot.cs:33-67`）是给 UI 的窄接口，只暴露 `SkillId / Casting / Cancel / IFrame / Downed / Dead / Hitstop / Hp / Shield / BurnStacks`，并用 `SameAs()` 做脏检查，避免每帧刷 UI。

## 12. 设计思路总结：为什么长这样

### 12.1 「技能 = 数据」，而不是「技能 = 类」

```
   ✗ 一个技能一个类：AttackSkill : Skill { ... }
        · 加技能要改代码、要重新编译
        · 技能的"手感"散落在构造函数的参数里

   ✓ 技能 = 引用一条时间轴 + 一组效果资产
        · 加技能 = 新建 2 个 .asset 并在 Database 里挂上（不改一行代码）
        · 时间轴是可读的：什么时候开判定盒、什么时候投弹，全在 Clips/Payloads 里
        · 代价：契约变多（id 对齐、InputToken 对齐、clip End ≤ Duration），
               所以用 Bake() 的四步校验把错误挡在开局前
```

### 12.2 只读共享 vs 实例状态：一条铁律

```
   BuffArenaData / TimelineSO / BuffArenaSkill / IEffect 实例
        ┌──────────────────────────────────────────────┐
        │  多角色共享，必须无状态                        │
        │  · 想加运行时字段？→ 加到角色组件上（如 _cooldownUntil）│
        │  · 想缓存？→ 用 Bake() 把结果烘进只读字段        │
        └──────────────────────────────────────────────┘
   TimelinePlayer / SkillDirectorComp / LocomotionComp
        ┌──────────────────────────────────────────────┐
        │  每角色一份，严禁共享                          │
        │  _live / _clipOpened / _payloadFired / _time  │
        │  都是实例状态 —— 共享会让两个角色互相顶掉时间轴   │
        └──────────────────────────────────────────────┘
```

### 12.3 半开区间：帧率无关的唯一办法

```
   统一规则：所有"到点"判定都是 (prev, now]，now 属于本帧、prev 已在上一帧处理过
       · clip 相交：End > prev && Start < next
       · clip 关闭：now >= End
       · payload：t > prev && t <= _time（首帧兜底 t <= _time）
   结果：掉帧、顿帧、变 dt 都不改变"每个时间点恰好触发一次"
```

### 12.4 意图队列（蜂腰）：让重入不可能发生

```
   输入 ──► 意图 ──► 队列 ──► 单一消费者
   · 阶段1 只投 SpawnProjectileIntent，阶段3 才生成 → 生成顺序稳定
   · 阶段3 只投 ApplyEffectsIntent，阶段4 才结算 → 不会边遍历边改血量
   · AoE 是唯一的例外（当场生成）：它的脉冲/寿命必须从生成帧起算
```

### 12.5 顿帧冻结模拟但不冻结表现

```
   Hitstop 期间：wall 钟继续、logic 钟 PauseLogic、但仍 FlushDespawn
   意义：命中反馈（卡肉）不影响表现节奏，UI/VFX/镜头照常，回收也不积压
```

### 12.6 三兄弟许可位：把源工程的 bool 变成数据

`AllowMove / AllowRotate / AllowSkill` 对应源工程 `SetCasterControlState(canMove, canRotate, canUseSkill)` 的三个参数。做成数据后：

```
   想加"施法中不能转但能走"的技能 → 改 AllowRotate=0，不动代码
   唯一样板：TL_3002 Roll（都不能）与 TL_3005 Fire2（不能施放）
```

## 13. 契约与坑（改代码前请先读这段）

| # | 坑 | 现象 | 出处 |
|---|---|---|---|
| 1 | **clip 的 `End` 大于 `Duration`** | `_time` 被 clamp 到 `Duration`，`MarkDueClose` 永远到不了 `End` → `_live` 永不为空 → `FlushPendingCloses` 永远返回 false → **技能永不结束**（`AllowSkill=0` 的时间轴会彻底锁死输入） | `Timeline.cs:358,418,443` |
| 2 | `InputToken` 改名 | 该键**静默失效**，不报错 | `Primitives.cs:158` |
| 3 | 单槽位输入缓冲 | 同时按两个键只有一个生效，另一个直接丢；且在 `AllowSkill=0` 的时间轴里会被 `Clear()` | `TagsInput.cs:40`、`BuffArenaGameplay.cs:222` |
| 4 | `payload` 的 `Time == 0` | 靠"首帧 `prev <= 0`"兜底；若某帧 dt 很大，`t=0` 与 `t=0.1` 会同帧投递 | `Timeline.cs:471` |
| 5 | `WarpSkillId` 只当闸门 | 传送技能的时间轴/动画**不会被播**；传送成功也没有 Cue | `BuffArenaGameplay.cs:237` |
| 6 | 追踪弹销毁时不清 `ProjectileTrackerComp` | 玩家永远以为"弹还在飞"，Fire4 再也射不出弹 | `RuntimeBodies.cs:193` |
| 7 | 技能播失败没退弹 | 需要在 `Play` 返回 false 时 `Refill(AmmoCost)` | `BuffArenaGameplay.cs:252` |
| 8 | 打断不走 `Stop()` | `Cancel` / `Invincible` 标签、`ClipSteer` 会泄漏（永久无敌/永久取消窗口） | `Timeline.cs:479` |
| 9 | `AI` 技能配了 `AmmoCost`/`InputToken` | 没意义：`WanderShooter` 不经过输入也不扣弹 | `BuffArenaGameplay.cs:297` |
| 10 | 内容里引用了不存在的 SpecId | `SpawnAoeEffect` 会 **throw**；`SpawnProjectileEffect` 则是静默不生成（`DrainSpawns` 里 `TryGet` 失败直接 return） | `Effects.cs:171`、`RuntimeBodies.cs:335` |
| 11 | 写回 `BuffArenaData` / `TimelineSO` | 重开局或对象池复用会串场 | `BuffArenaGameplay.cs:128` |
| 12 | 未引用的资产 | `AD_4101`、`AD_4103` 目前没有任何时间轴/弹道引用它们（是留给后续技能的内容，不是错误） | 全内容 grep `SpecId: 4101/4103` |
